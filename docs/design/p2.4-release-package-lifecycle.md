# P2.4 release and package lifecycle

## Objective

Make the harness distributable through a controlled pnpm package and a
reviewed release process. A release must be reproducible from the merged
candidate, prove its package contents, and preserve Gentle-AI ownership of
managed assets.

## Decisions

1. `package.json` is the package metadata source of truth. The implementation
   must stop duplicating the harness version in runtime constants; generated
   or imported metadata must expose the same version to the CLI and state
   reports.
2. Releases use SemVer and a changelog entry committed before publication.
   Version bumps are explicit commits/PRs, never an implicit mutation during
   `pnpm pack` or CI.
3. `pnpm pack --json` is the package boundary contract. CI validates the
   tarball file list and rejects build output, tests, source maps containing
   workspace paths, secrets, and Gentle-AI managed assets.
4. Publication is a protected delivery action. It requires a merged PR,
   green required checks, a clean tag candidate, and an explicit registry
   credential; CI may prepare and attest a package but does not publish from
   unreviewed pull requests.

## Ownership boundary

The package owns the harness CLI, compiled `dist/` output, and portable
`templates/`. It does **not** own `.ai/`, `.codex/`, `.claude/`, `.pi/`,
`.opencode/`, `~/.gentle-ai`, or any generated assets managed by Gentle-AI.
Package tests must assert this boundary rather than relying on a human review
of the tarball.

## Release states

```text
WORKING → CANDIDATE → VERIFIED → TAGGED → PUBLISHED
                     ↘ BLOCKED
```

- `WORKING`: normal development; no registry side effect.
- `CANDIDATE`: version/changelog and package manifest are proposed in a PR.
- `VERIFIED`: typecheck, tests, package-content audit, and CI gates pass for
  the exact candidate commit.
- `TAGGED`: an annotated `vX.Y.Z` tag points at the verified merge commit.
- `PUBLISHED`: the tarball digest and registry result are recorded.
- Any failed check, dirty candidate, version mismatch, or registry error is
  `BLOCKED`; it must not be described as published.

## Required checks

| Check | Evidence | Failure behavior |
|---|---|---|
| Version consistency | package metadata equals CLI/state version | Block candidate |
| Changelog | versioned entry with user-visible changes and migration notes | Block candidate |
| Build/test | `pnpm typecheck`, `pnpm test` | Required CI failure |
| Package boundary | deterministic `pnpm pack --json` audit | Required CI failure |
| Governance | approved issue, reviewed PR, required checks | No tag/publication |
| Gentle-AI ownership | managed paths absent from tarball | Block candidate |

## Implementation slices

1. Add a deterministic package-audit command and tests for allowed/forbidden
   paths, version consistency, and tarball metadata.
2. Add changelog/version validation and a release checklist/CI workflow that
   prepares a candidate without publishing it.
3. Add the protected tag/publication workflow and record the tarball digest
   after a real registry publication.

## Out of scope

This design does not select a registry, create credentials, publish a package,
or update Gentle-AI. Those actions require an explicit delivery decision and
external evidence.
